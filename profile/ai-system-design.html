PHASE 1 Requirements, Scoping & Feasibility Analysis
Read moreShow less

The single most expensive mistake in AI system design is applying a probabilistic engine to a deterministic problem — this phase exists to catch that before any architecture work starts.

Before touching any architecture, this phase exists to answer one question honestly: should this even be an LLM system? Most production AI failures trace back to skipping this phase — teams reach for an LLM because it's exciting, not because the problem demands probabilistic reasoning. Everything downstream (cost, latency, reliability) gets harder to fix later than to prevent here.

phase objectives

Deterministic vs. probabilistic classification is the foundational filter. Ask: does this task have one correct, computable answer given the inputs? Deterministic — "what's this customer's account balance?" (a database query), "is this date within the return window?" (a comparison) — has exact answers; feeding it through an LLM adds latency, cost, and a non-zero chance of a wrong answer for something a SELECT statement gets right 100% of the time. Probabilistic — "summarize this contract's risk clauses," "what does this customer actually want, given this messy support ticket?" — has no single correct string, only better or worse answers; this is where LLMs earn their cost. Getting this wrong in one direction (LLM for deterministic work) builds an unreliable, expensive lookup table; getting it wrong the other way (hardcoded rules for genuinely open-ended language tasks) means the system breaks the moment inputs vary from what was anticipated.

Token economics, ROI modeling, and NFRs are three things bundled together, each answering a different question. Token economics: what does one interaction cost? (input tokens + output tokens — output is typically 3–5x pricier per token — × expected volume). This isn't a nice-to-have estimate; it's often the deciding factor on whether a feature ships at all. ROI modeling: cost of the AI system vs. cost of the alternative (usually human labor, or doing nothing) — a support-ticket triage assistant costing $0.02/ticket to save 4 minutes of agent time worth $0.60 is a strong case; one costing $0.15/ticket to save 30 seconds is a harder sell. NFRs (Non-Functional Requirements), specifically: TTFT (Time-To-First-Token) governs perceived responsiveness — a 3-second TTFT feels broken even if the full answer streams in fast after; throughput is how many concurrent requests/sessions the system must sustain; latency budget is the total time ceiling for a complete response, broken down per component. These numbers get derived from actual user expectations and written down before architecture decisions, because they constrain which techniques are even viable — a 500ms latency budget eliminates most multi-hop agentic RAG designs before a single box gets drawn.

system components & topologies

The decision tree gate is the practical embodiment of the deterministic/probabilistic split: every incoming request first hits a gate that asks "can deterministic logic handle this?" If yes, it's routed to a rules engine or direct data lookup — no LLM involved at all. Only the residual, genuinely ambiguous cases proceed to a model call. The architectural implication: the system isn't "an LLM app" — it's a hybrid system with an LLM as one component, gated behind a cheap, fast classifier or explicit routing logic. This is why the cost reduction (60–80%) is real and not theoretical — it comes from not paying LLM prices for the 60–80% of traffic that never needed an LLM in the first place.

The latency budget waterfall. Instead of one number ("under 3 seconds"), the budget is allocated across every hop the request makes: Network (50ms) → Auth (30ms) → Retrieval (400ms) → Generation (2000ms) → Post-processing (100ms) = 2,580ms total. Breaking it down at design time, before anything is built, matters because when the SLA gets violated in production, the team needs to know where to look without guessing — if generation is budgeted at 2000ms and retrieval at 400ms, and responses are running 4 seconds, it's immediately clear whether to check retrieval (bad index, no caching), generation (wrong model tier, no streaming), or something entirely unbudgeted like a forgotten guardrail check. Without this waterfall, debugging latency becomes archaeology.

tooling & tech stack

  • Cost modeling: usually a spreadsheet seeded with real provider pricing (Anthropic/OpenAI/Google per-token rates) times a volume forecast — this phase is about the prediction, not the measurement. Helicone/Langfuse come in after launch to validate whether the model matched reality.
  • Requirements/traceability: Jira/Linear for tracking the requirement itself, but the important artifact is the ADR (Architecture Decision Record) — a short markdown file in the repo like docs/adr/0001-use-rag-over-finetune.md that captures why a decision was made, not just what was decided. This matters enormously at staff level: six months later, someone will ask "why didn't we just fine-tune?" and the ADR is the answer, not someone's memory.
  • Load/latency estimation: back-of-envelope math using Little's Law (L = λW — the relationship between concurrent requests, arrival rate, and time-in-system) to sanity-check whether the throughput target is even physically plausible given the latency budget, before anything is built. Validated later with actual load tests (k6, Locust) once a prototype exists.

The pattern across all three: estimate cheaply and on paper first, validate expensively and with real tools second.

trade-offs & challenges

The "let's use an LLM" trap: teams skip the deterministic/probabilistic classification and default to an LLM because it's the exciting new tool. The failure mode is specific and dangerous — applying non-deterministic logic to something that requires 100% reproducibility (tax calculations, eligibility determinations, compliance checks). An LLM might get the tax calculation right 99% of the time, but "99% correct" is not an acceptable standard for arithmetic that used to be a formula. Mitigation: require a written justification any time probabilistic logic touches a compliance-sensitive computation — this forces the deterministic option to be considered and rejected explicitly, not skipped silently.
TTFT vs. throughput tension: streaming responses makes TTFT look great — the user sees output almost immediately — but streaming means holding a connection open for the entire generation, not just until the first token. Under high concurrency this ties up connection pool resources for longer, straining the pool exactly when it's needed most. Mitigation: use multiplexed protocols like Server-Sent Events (SSE) rather than raw long-lived sockets, which handle many concurrent open streams far more efficiently.
Cost model blind spots: two common ones. Teams model the average cost per interaction, but agentic/retry-heavy flows have a much fatter tail — a query that triggers a self-correction loop or a multi-step agent chain can cost 5–10x the average, so budgeting on average, not P90, means the bill surprises everyone the first month real traffic hits. And output tokens are priced 3–5x higher than input tokens — a system that returns long, detailed answers looks cheap in a naive "tokens × price" spreadsheet if only the prompt was counted.
PHASE 2 Architectural Decision Frameworks & Model Selection
Read moreShow less

Phase 1 told you whether to use an LLM at all. Phase 2 commits you to which technique and which model — and to a decision-making process you can defend later, instead of "we picked GPT-4 because everyone does."

Phase 1 told you whether to use an LLM. Phase 2 tells you which technique and which model — and just as importantly, it commits you to a decision-making process you can defend later, instead of "we picked GPT-4 because everyone does."

phase objectives

  • Build vs. Buy, and technique selection. "Build vs. Buy" means foundation model API (Anthropic/OpenAI/Google) vs. self-hosted open-source model vs. a fully custom model trained from scratch — and in practice, "train from scratch" is almost never right for application teams; it's reserved for organizations with a model lab's data scale and budget. The real decision is API vs. self-hosted OSS, hinging on data sensitivity, cost at scale, and latency control. The technique-selection ladder — Prompt Engineering → RAG → GraphRAG → Fine-Tuning → RLHF/DPO — is ordered by cost and complexity, and the objective is explicit: pick the minimum viable technique that meets the NFRs from Phase 1. This is a discipline, not a preference — teams reach for fine-tuning because it feels like "real ML work," when prompt engineering or RAG would have solved the actual problem far more cheaply. The job of this phase is forcing a justification for skipping each cheaper rung before reaching for the next one.
  • Multi-model routing strategy. Not every query deserves the most expensive, most capable model. The objective is avoiding both single-model lock-in and single-model cost inefficiency: a routing policy decides, per-request, which model handles it, based on task complexity, required context window, and cost target. This is a deliverable in its own right — a documented policy (even if implemented as a simple classifier) for why request type X goes to model tier Y.

system components & topologies

The decision matrix is the concrete tool that makes the ladder non-arbitrary. Score the problem 1–5 across five axes — data freshness need, domain specificity, latency sensitivity, cost ceiling, and explainability requirement — and the routing logic follows directly: static facts plus a tone/style shift → Prompt Engineering (no external data needed, the model already "knows" the content); external, private, or frequently-changing knowledge → RAG (you're not changing what the model knows how to do, you're changing what facts it has access to at query time); multi-hop reasoning over interconnected entities — e.g. "does this vendor's subsidiary violate our compliance policy through an indirect ownership chain" → GraphRAG (plain vector RAG retrieves similar chunks, it doesn't traverse relationships); durably changing behavior, style, or latent reasoning pattern rather than adding facts → Fine-tuning/LoRA (e.g. a legal team's mandated structured output format, applied every time without re-explaining it in every prompt).

The model router topology is a cascade (or mixture-of-models) pattern: a cheap, fast component — often a small LLM or even just an embedding-based classifier — sits in front of the model gateway and looks at the incoming query to decide its complexity tier. Simple/short queries route to a fast, cheap model (Haiku-class); complex reasoning gets the large model (Opus-class); code gets a code-specialized model. The architectural insight worth internalizing: the router itself is also a model call, so it has to be cheap enough that running it on every request doesn't erase the savings from routing correctly — which is why routers are usually small/fast models or non-LLM classifiers, never another expensive model call.

tooling & tech stack

  • Proprietary APIs (buy side): Anthropic Claude (via Claude Platform, AWS Bedrock, or Google Vertex), OpenAI, Google Gemini — frontier capability, managed reliability, zero infrastructure overhead.
  • Open-source self-hosted (build side): Llama, Mistral, Qwen, served through vLLM or TGI (Text Generation Inference) for optimized batched inference, or Ray Serve when serving needs to scale across a cluster — total data residency and inference-stack control, at the cost of owning the ops burden too.
  • Fine-tuning: LoRA/QLoRA via Hugging Face PEFT or Axolotl for parameter-efficient fine-tuning — training small adapter layers rather than the whole model, dramatically cheaper and faster than full fine-tuning. Managed fine-tuning is also available directly through provider consoles for teams that don't want to own the training infrastructure.
  • Routing frameworks: LiteLLM is the most common choice — a model-agnostic gateway that routes/fails over across providers behind a unified API. OpenRouter and Martian serve similar purposes; for anything beyond simple routing rules, teams often build a custom classifier + gateway combination.
  • GraphRAG: Neo4j (the standard graph database), the Microsoft GraphRAG library (automatic entity/relationship extraction from unstructured text), or Amazon Neptune for AWS-native deployments.

trade-offs & challenges

RAG vs. fine-tuning confusion is the single most common architectural mistake at this phase, so it's worth being precise. RAG injects facts at inference time — update the underlying documents and the system's knowledge updates immediately, no retraining, and it's auditable: you can point to the exact chunk that produced an answer. The cost is architectural complexity and added latency (a retrieval hop before generation), plus a whole new failure surface (bad retrieval = bad answer, even with a perfect model). Fine-tuning bakes in behavior — format, voice, task-specialization, a particular way of reasoning through a narrow problem type. It's fast at inference (no retrieval hop) but expensive to update (every change needs a retraining/adapter-swap cycle), carries a real risk of catastrophic forgetting (the model gets worse at things it used to do well while learning the new behavior), and is much harder to audit, since the knowledge is now distributed across the weights rather than pointing to "the fact" that caused an output. The rule of thumb worth memorizing: RAG for facts, fine-tuning for format/voice/task-specialization — fine-tuning to "teach the model about our product catalog" is almost always a RAG problem wearing a fine-tuning costume.

GraphRAG overhead: building and maintaining a knowledge graph isn't a one-time cost — entity resolution (is "Acme Corp" the same as "Acme Corporation, Inc." in a different document?) and relationship extraction are standing engineering commitments. Only worth it when multi-hop relational reasoning measurably improves answer quality over plain vector RAG. Mitigation is empirical, not architectural: run an A/B comparison against plain vector RAG on the actual eval set before committing to the graph infrastructure — don't build the graph because it sounds more sophisticated.
Vendor lock-in risk: hardcoding prompts and tool schemas to one provider's specific quirks (message format, function-calling syntax, system prompt conventions) means switching providers later requires rewriting significant application logic, not just changing a config value. Mitigation: abstract behind a gateway (LiteLLM or a custom equivalent) using provider-agnostic message schemas, and always maintain a documented fallback model list — this also directly enables the failover topology built in Phase 6.
Router misclassification — the subtle, dangerous one: a router that sends a genuinely complex query to a cheap model doesn't throw an error, it just silently returns a worse answer. No exception to catch, no alert to fire — worse than a crash, because crashes get noticed while complex-but-wrong answers erode trust slowly and invisibly. Mitigation: build confidence thresholds into the router (default to the safer/larger model when complexity classification isn't confident, rather than the cheaper one), and validate routing decisions with shadow-routing evaluation — run the router's decisions against a held-out eval set and compare against what a human or a larger model would have chosen, before trusting it in production.
PHASE 3 Data Engineering, Vectorization & Governance
Read moreShow less

Building the retrieval substrate that grounds the system in truth — and enforcing access control at the retrieval layer, not just the UI.

If Phase 2 decided the system needs RAG, Phase 3 is where the thing RAG actually depends on gets built: a retrieval substrate that's accurate, fresh enough, and secure enough to trust in production. This is also where most "the AI gave a wrong answer" bugs really originate — not from the model, but from bad retrieval feeding it bad context.

phase objectives

  • Ingestion pipelines — idempotent, incremental, lineage-tracked. Idempotent: re-running the pipeline on the same document shouldn't create duplicate chunks/vectors — without explicit dedup logic (a content hash or document ID + version check), a scheduler retry silently doubles the index over time. Incremental: the entire corpus shouldn't need reprocessing every time one document changes — this is what keeps "index freshness" sustainable rather than an ever-more-expensive nightly full rebuild. Lineage-tracked: every chunk traces back to its source document, version, and ingestion timestamp — not bureaucracy, but what makes "why did the assistant say that" and "this source doc just changed, what needs re-indexing" answerable.
  • A chunking + embedding strategy tuned to domain structure. The goal isn't "chunk the documents" — it's chunking them in a way that matches how they're actually structured. A legal contract, a Slack export, and an API reference all have completely different natural units of meaning; getting this wrong is one of the most common causes of vague or fragmented RAG answers.
  • Hybrid retrieval tuned for recall and precision. Vector search alone misses exact-match cases (a SKU, an error code, a proper noun); keyword search alone misses semantic paraphrases. The objective is combining both — plus graph traversal when Phase 2 calls for it — and tuning the combination against real queries, not just wiring them together and hoping.
  • Governance — PII masking, RBAC/ABAC at the retrieval layer. Access control has to be enforced where retrieval happens, not somewhere else in the stack like the UI — this is the single most consequential point in the whole phase.

system components & topologies

The ingestion pipeline topology: source connectors → layout-aware parsers → cleaning/normalization → chunking → embedding → indexing → metadata tagging (source, ACL, timestamp, version). "Layout-aware" matters enormously for real enterprise documents — a naive text extractor on a PDF with tables interleaves table cells with surrounding paragraph text in an order that makes no sense, destroying the semantic unit being chunked. Metadata tagging happens at ingestion, not as an afterthought: ACL tags, source system, and version attach to each chunk before it ever enters the index, which is what makes retrieval-time filtering possible later.

  • Chunking strategies: fixed-size with overlap (the baseline — split every N tokens with overlap so a sentence never gets cut at a boundary; simple, works everywhere, optimal nowhere); semantic chunking (split where consecutive sentences' embeddings diverge significantly — a topic-shift detector — producing variable-length but semantically coherent chunks); structure-aware chunking (respect markdown headers, table boundaries, code blocks — a chunk should never split a table in half or cut a function mid-body); small-to-big retrieval (embed small, precise chunks for accurate matching, but return the parent section to the model once one is retrieved — solving the real tension that small chunks match queries precisely but often lack enough context alone).

Hybrid search topology: query → [BM25/keyword index] + [dense vector index] + [optional graph traversal] → fusion (Reciprocal Rank Fusion or a cross-encoder reranker) → top-K to the model. BM25/keyword (Elasticsearch/OpenSearch) catches exact terms, codes, and names; dense vector (Pinecone/Weaviate/pgvector) catches semantic/paraphrase matches. RRF is a simple, effective way to combine two ranked lists without calibrating their scores against each other. A cross-encoder reranker (Cohere Rerank, BGE-reranker) goes further — it re-scores top candidates by jointly encoding query + document together, more accurate but too slow to run over the whole corpus, so it only reranks the top-K from the cheaper first pass.

Governance enforcement point — pre-filter, not post-filter. This is the component that deserves the most attention. ACL/metadata filters get applied inside the vector DB query itself — as a pre-filter restricting which vectors are even scored — never as a step that runs after retrieval to strip out results the user shouldn't see. If top-20 results are retrieved first and unauthorized ones filtered out afterward, two things go wrong: fewer than the K results wanted may remain (or zero, if everything relevant happened to be restricted), so context quietly degrades for no visible reason; and worse, some retrieval implementations expose scoring/ranking signals, or a clever prompt can get the model to reference something it "saw" during retrieval even if it wasn't in the final filtered set. Filtering before scoring means restricted documents are never retrieved, never scored, and never touch the model's context window — there's no path for leakage because the data was never in the candidate set.

tooling & tech stack

  • Vector DBs: Pinecone, Weaviate, Qdrant, Milvus — dedicated vector databases built for this. pgvector is the pragmatic choice when Postgres is already running and another piece of infrastructure isn't wanted — fewer moving parts, at the cost of some scale ceiling versus purpose-built vector DBs.
  • Ingestion/orchestration: Airflow or Dagster for scheduling and dependency management; LlamaIndex/LangChain data connectors for common source integrations; Unstructured.io specifically for robust, layout-aware parsing of PDFs, Word docs, and HTML.
  • Embeddings: OpenAI text-embedding-3, Cohere Embed, Voyage AI (managed/API), or open-source BGE/E5 models when self-hosting is needed for data residency or cost.
  • Reranking: Cohere Rerank (managed API) or BGE-reranker-large (self-hosted).
  • PII/governance: Presidio (Microsoft) for detecting and masking PII at ingestion; Immuta/Collibra for data lineage and access governance at the platform level; OPA (Open Policy Agent) for expressing ABAC rules as policy-as-code evaluated at query time — this is what actually implements the pre-filter enforcement point above.

trade-offs & challenges

Chunking is a tuning knob, not a one-time decision: too-small chunks lose surrounding context, producing fragmented, incomplete-feeling answers; too-large chunks dilute the embedding — a 2000-token chunk covering five subtopics produces a "smeared" embedding that doesn't match any single query well, and eats into the context budget faster. Mitigation: run chunk-size sweeps against the eval set (Phase 5) and measure retrieval quality empirically, rather than picking a number because it "seemed reasonable."
Embedding model drift: switching embedding models — even to a "better" one — puts old and new vectors in different geometric spaces that aren't comparable; they can't be mixed in the same index and expected to work. Changing embedding models is a full corpus re-embedding migration, not a config change, and needs to be planned and resourced as such (compute cost, downtime/blue-green strategy, validation against the eval set before cutover).
RBAC-at-retrieval is the #1 security gap in RAG systems: many teams enforce access control only in the application layer — checking permissions before showing the final answer — while the vector DB itself has no ACL awareness. A sufficiently crafted prompt can sometimes get the model to retrieve and reference chunks the requesting user shouldn't have access to, because nothing stopped those chunks from being retrieved in the first place, only from being displayed through the normal path. This is the pre-filter vs. post-filter distinction above, and it's worth treating as a hard architectural rule, not a best-effort guideline.
Freshness vs. cost: real-time re-indexing on every document change is expensive and often unnecessary — most production systems use scheduled incremental re-indexing (e.g., every 15 minutes via change-data-capture) with an explicitly documented staleness SLA ("information may be up to 15 minutes stale"). The mitigation isn't "make it instant" — it's making the staleness bound known and acceptable, which is a product decision as much as an engineering one.
PII leakage through retrieval: masking PII at ingestion can backfire — masking a customer's name in a support ticket before embedding makes that chunk useless for retrieving the ticket when the same customer asks a follow-up question later, since the embedding no longer carries the identifying signal that made it relevant. Mitigation: separate the two concerns — mask for indexing/embedding if compliance requires it, but gate access to the original unmasked text behind the same ABAC policy used for retrieval, so the right person can still see the real content while it isn't indiscriminately searchable.
PHASE 4 Agentic Workflows, Memory & Orchestration
Read moreShow less

Choosing an agent topology proportional to task complexity — and making tool-calling deterministic and safe.

Phases 1–3 got you a system that can answer questions grounded in data. Phase 4 is where the system starts doing things — taking multi-step actions, calling tools, and maintaining state across a conversation or across sessions. This is also where over-engineering does the most damage, so the discipline here matters as much as the patterns.

phase objectives

  • Choose agent topology proportional to task complexity. This is stated as a constraint, not just a design choice: don't over-engineer a single Q&A bot into a multi-agent swarm. "Multi-agent" sounds more sophisticated and is genuinely tempting to reach for — but every agent-to-agent handoff is a place where context gets lost, latency accumulates, and cost multiplies. Default posture: start with the simplest topology that could work, and only add agents when the task genuinely decomposes into distinct roles.
  • Make tool-calling deterministic and safe. An LLM deciding which tool to call and what arguments to pass is inherently probabilistic — but the execution of that tool shouldn't compound that uncertainty. The objective is validated schemas (the tool call's shape is checked before it runs) and idempotent side effects (calling the same tool twice with the same inputs doesn't cause double harm — double-charging, double-sending). Same principle as Phase 1's deterministic/probabilistic split, applied one layer deeper: the decision to call a tool can be probabilistic, but its execution should be as deterministic and safe as any other backend operation.
  • Design memory: short-term vs. long-term. Two genuinely different problems get lumped under "memory," and the objective is to keep them architecturally distinct — short-term is what's been said in this conversation, needed for coherence within a session; long-term is what the system should remember about a user or entity across sessions (preferences, past decisions, recurring facts). Conflating these leads to a memory system that's neither a good conversation buffer nor a good persistent knowledge store.

system components & topologies

Single-agent ReAct loop: LLM reasons → calls a tool → observes result → reasons again → responds. This is the workhorse pattern for bounded, single-domain tasks — "look up this order and summarize it," "check this customer's account status and answer their question." One model, looping through reason-act-observe until it has enough information to respond. Most production agentic systems should live here — it's simple to debug (one trace, one model's reasoning to inspect) and cheap (one model's worth of calls, not N).

Stateful multi-agent orchestration is for tasks that naturally decompose into distinct roles — e.g. "research → draft → review → send," where each stage genuinely benefits from a different prompt, different tool access, or even a different model tier. LangGraph models the workflow as an explicit state machine over agent nodes — crucially, it supports cycles (an agent can loop back, e.g. a critic sends work back to a drafter), checkpointing (state persisted at each transition, so the workflow survives a crash), and human-in-the-loop interrupts (the graph pauses at a defined point and waits for human approval before continuing — essential for anything with real-world side effects). AutoGen/CrewAI model multi-agent collaboration more as a conversation between agents with defined personas/roles, rather than an explicit state graph — a good fit when the interaction pattern is closer to "agents debating/collaborating" than "a fixed pipeline with defined stages." The decision between these isn't about which is "better" — it's about whether the workflow is better modeled as a state machine with explicit transitions (LangGraph) or a role-based conversation (AutoGen/CrewAI).

Tool-calling mechanics: strict JSON-schema-validated function definitions — the tool's expected inputs are defined as a schema, and every call is validated against it before execution, catching a hallucinated parameter (e.g. an order ID in the wrong format) before it ever reaches a real system. Sandboxed execution with timeouts — tool execution happens in an isolated context with a hard timeout, so a hanging or malicious tool call can't stall the whole agent loop indefinitely. Idempotency keys — any tool with side effects gets called with a unique key per logical operation, so if the agent (or the underlying infrastructure) retries the call, the receiving system recognizes it as "already done" rather than executing it twice. This is standard practice in distributed systems generally; it's just newly critical here because LLM-driven retries are more common and less predictable than traditional application retries.

Memory architecture. Short-term: a sliding window (keep the last N turns) or a summarization-compressed buffer (older turns periodically summarized to save context space), stored in something fast like Redis, scoped strictly to the active session. Long-term: a separate vector-indexed memory store, per-user or per-org, that agents explicitly write to and read from. The key word is "separate" — this is architecturally distinct from the Phase 3 RAG knowledge base, because RAG holds corpus/factual knowledge (the same for every user), while long-term memory holds episodic/personal knowledge (specific to a user or interaction history). Mixing them means a memory store that's neither a clean corpus nor a clean personal record.

State persistence. For any agentic workflow that runs longer than a single request/response (multi-step, possibly with a human-in-the-loop pause), the in-progress state needs to be checkpointed somewhere durable — LangGraph's built-in checkpointers, or a plain Postgres/DynamoDB state table when building this from scratch. Without this, a process restart or a long pause-for-approval loses all progress and the workflow has to start over.

tooling & tech stack

  • Orchestration: LangGraph, AutoGen, CrewAI, Microsoft Semantic Kernel — or, notably, a bare state machine like Temporal or AWS Step Functions, when maximum control is wanted without agent-framework abstractions at all.
  • Durable execution: Temporal.io is increasingly used underneath agent orchestrators specifically to guarantee exactly-once tool execution and long-running workflow durability — the same durable-execution problem space as orchestrating distributed workflows in a microservices system, just with an LLM making some of the branching decisions instead of pure business logic.
  • Memory stores: Redis for short-term; Zep, Mem0, or a dedicated namespace in an existing vector DB for long-term semantic memory.
  • Tool schema validation: Pydantic in Python or Zod in TypeScript — the mechanism that enforces strict I/O contracts on every tool definition.

trade-offs & challenges

Multi-agent overhead: every hand-off between agents is a full extra LLM call, and every extra LLM call is a place where an intermediate summary can be slightly wrong, slightly lossy, or misinterpreted by the next agent in the chain. N agents means roughly N times the latency and cost of a single-agent approach, for a task a single well-designed agent loop might have solved directly. Default should always be single-agent; escalate to multi-agent only when the task has genuine separation-of-concerns needs (different tool access per role, different model tiers per subtask) or benefits from parallelism (independent subtasks that can run concurrently).
Non-deterministic tool selection: LLMs sometimes pick the wrong tool, or the right tool with a hallucinated parameter. The mitigation isn't "make the model smarter" — it's architectural: constrain the active toolset per conversation state. Don't expose 40 tools simultaneously and hope the model picks correctly; use routing or sub-agents to narrow what's available at any given point, so the model is choosing among 3–5 relevant tools, not searching a haystack of 40. Combined with strict input validation, this catches most tool-calling failures before they cause harm.
Runaway loops: agentic loops can spiral — infinite retries when a tool keeps failing, or a planner and a critic agent disagreeing indefinitely and bouncing work back and forth. This has a real cost dimension (every iteration is more tokens spent) and a real reliability dimension (the user is waiting on a task that will never converge). Mitigation: a hard max-iteration count and a token/cost ceiling per task, with a defined graceful-degradation path — "hand this off to a human" — rather than the system silently failing or burning budget indefinitely.
Memory pollution: long-term memory written to indiscriminately accumulates stale or contradictory facts over time — a user's preference from six months ago that's since changed, or two agents writing conflicting "facts" to the same memory store. Mitigation: enforce memory write policies (only persist explicitly confirmed facts, not every inference the agent made), periodically consolidate/decay old memory entries, and define a conflict-resolution rule on read — most commonly most-recent-wins, or explicit versioning so contradictions are visible rather than silently overwritten.

The throughline here is the same discipline as Phase 2's "minimum viable technique" principle, applied to orchestration: default to the simplest agent topology, and treat every added agent, every persisted memory, and every tool exposure as something that has to earn its place — because each one is a place where the system can quietly get worse rather than fail loudly.

PHASE 5 Guardrails, Security & Evaluation
Read moreShow less

Making the system safe to expose to real users, and measurable enough to improve with confidence — in CI/CD, not ad hoc.

Phases 1–4 built a system that retrieves, reasons, and acts. Phase 5 is where it gets made safe to expose to real users and measurable enough to trust your own claims about it. This phase is often treated as an afterthought — bolted on right before launch — but it's actually load-bearing: without it, there's no way to know whether a change made the system better or worse, and no defense against the specific ways LLM systems get attacked.

phase objectives

Defend against the OWASP Top 10 for LLMs. This is the security baseline, and it's worth understanding why LLM applications need a distinct threat model from traditional web apps. In a normal web app, user input is validated and sanitized at the boundary and the backend logic is trusted. In an LLM system, the model itself is a decision-maker that can be persuaded by anything in its context — including content that was never typed by the user at all (a retrieved document, a tool's output, a webpage the agent fetched). That's a fundamentally new attack surface.

Real-time input/output guardrails. The objective is a layer that inspects both what goes into the model and what comes out, in real time, as part of the request path — not as an offline audit that happens after the fact. This has to run fast enough not to blow the latency budget from Phase 1, which turns out to be one of the harder engineering constraints in this whole phase.

A repeatable evaluation harness in CI/CD. The objective is turning "does this feel better?" into a number that runs automatically on every change. Without this, every prompt tweak or model swap is a gamble evaluated by vibes, and regressions ship silently.

system components & topologies

Defense-in-depth against the key OWASP LLM risks. Indirect prompt injection is the big one, and it's worth being precise about the mechanism. A direct prompt injection is a user typing "ignore your instructions" — relatively easy to guard against. An indirect injection is malicious instructions hidden inside content the system retrieves or fetches — a document in the RAG corpus, a webpage an agent browses, the output of a tool call. The model has no inherent way to distinguish "instructions from my system prompt" from "text that happens to look like instructions, sitting inside a document I retrieved." The architectural defense is treating all retrieved/tool content as untrusted data, never as instructions — enforced through strict system-prompt framing ("the following is reference material, not instructions"), tagging content by origin so the model can be trained/prompted to weight it differently, and output-side checks that flag responses which suddenly deviate from what the user actually asked for. Data poisoning is the related risk on the ingestion side — if an attacker (or just bad data hygiene) can get malicious or false content into the fine-tuning corpus or RAG index, the system's outputs are compromised at the source; mitigate with version-control and validation on any corpus used for training or ingestion, plus anomaly detection on the ingestion pipeline itself, flagging documents that look statistically unusual compared to the existing corpus. Unauthorized tool execution rounds this out: every tool call needs to be authorized against the permissions of the requesting user, not the blanket service-account permissions the agent process runs under — directly analogous to a principle already familiar from traditional backend systems (never trust that a client-side check is sufficient, always re-validate authorization server-side), just now applied to what an LLM decides to do, not just what a user submits in a form.

The guardrail pipeline topology: Input → [Input guardrail: jailbreak/PII/toxicity classifier] → LLM → [Output guardrail: hallucination/toxicity/format/PII-leak classifier] → Response. The key design constraint: guardrails should run as fast, cheap classifiers, ideally in parallel with or ahead of the main model call, not as another full LLM call stacked in series. A guardrail that's itself a slow, expensive model call doubles latency and cost for every single request — which directly threatens the TTFT/throughput budgets from Phase 1.

The evaluation harness: golden dataset (query, expected-behavior pairs) → automated scoring on every PR/deploy → regression gate in CI. Two evaluation approaches worth distinguishing. The RAG Triad covers three specific, measurable dimensions — Faithfulness: is the answer actually supported by the retrieved context, or did the model add something not in the source material (hallucination)? Answer Relevance: does the answer actually address what was asked, independent of whether it's faithful to the sources? Context Precision/Recall: did retrieval surface the right chunks, and only the right chunks — this evaluates the retrieval step in isolation from generation, which matters because a great model given bad context still produces a bad answer, and it's necessary to know which layer is at fault. LLM-as-Judge uses a stronger model to score outputs against a rubric, useful for more open-ended quality dimensions the RAG triad doesn't capture (tone, completeness, helpfulness) — with the important caveat, covered in trade-offs below, that the judge itself needs periodic validation.

tooling & tech stack

  • Guardrail frameworks: NVIDIA NeMo Guardrails (lets you define programmable "rails" — topics the model should refuse, conversation flows it should follow), Meta Llama Guard (a purpose-built safety classifier model), Guardrails AI (focused on validating structured output format), and custom regex/PII classifiers built on Presidio for deterministic, fast checks that don't need a model call at all.
  • Eval frameworks: Ragas (implements the RAG triad metrics specifically), TruLens, DeepEval, promptfoo (built specifically for CI-friendly prompt regression testing — the one to wire directly into a GitHub Actions pipeline), and Arize Phoenix eval templates.
  • Security testing: garak (an LLM vulnerability scanner, analogous to a security scanner run against a traditional web app), promptfoo's red-teaming plugins, and manual red-team playbooks explicitly mapped to the OWASP LLM Top 10 categories so testing coverage is traceable to a known threat list.

trade-offs & challenges

Guardrail latency tax: stacking multiple classifier calls — one before generation, one after — can meaningfully add to TTFT, especially if any of them are themselves LLM-based rather than lightweight classifiers. Mitigation: run cheap, deterministic checks (regex, small classifiers, Presidio-style PII detection) inline in the main request path, and reserve heavier LLM-based guardrails for cases flagged as ambiguous by the cheap first pass — the same cascade principle from Phase 2's model routing, applied to safety checks instead of task complexity.
False positives erode trust: guardrails tuned on generic defaults tend to over-block in specialized domains — a healthcare or legal assistant will routinely encounter vocabulary (symptoms, injury descriptions, legal terminology around violence or abuse in a case file) that a generic toxicity classifier flags as unsafe, when it's completely normal for that domain. Mitigation: domain-tuned guardrail thresholds validated against real production query logs, not generic benchmark defaults.
LLM-as-Judge is not ground truth: a judge model has its own biases — commonly favoring longer, more confident-sounding, or more verbose answers regardless of actual correctness. Treating judge scores as objective truth without calibration risks optimizing the system toward "sounds better to another LLM" rather than "is actually better for the user." Mitigation: periodically sample judge scores against a human-labeled set and measure inter-rater agreement — if the judge and human raters disagree often, the judge needs recalibration (different rubric, different judge model, or additional context) before it's trusted to gate deployments.
Eval sets go stale: a golden eval set built at launch reflects the query distribution and corpus at that time. As the corpus grows, user behavior shifts, and new edge cases emerge in production, a static eval set stops representing real traffic — meaning the CI gate can pass cleanly while real-world quality quietly degrades on cases the eval set never covered. Mitigation: continuously mine production logs (connecting directly to Phase 7's feedback loops) for new hard cases — especially flagged or low-scoring interactions — and fold them into the eval set on a regular cadence, so it evolves alongside the system it's testing.

The throughline connecting this phase to everything before: Phase 3 taught that where you enforce something determines whether it works (retrieval-layer RBAC, not UI-layer). Phase 5 applies the same lesson to trust and safety — untrusted content has to be treated as untrusted at the point it enters the model's context, not filtered after the fact, and quality has to be measured continuously against real traffic, not just at a one-time launch gate.

PHASE 6 LLMOps, Infrastructure & Resilience
Read moreShow less

Operationalizing for production-scale reliability and cost control — treating prompts, models, and indexes as first-class deployable artifacts.

Phases 1–5 designed a system that's architecturally sound and safe. Phase 6 is where it gets made to survive production — real traffic spikes, provider outages, rate limits, and the ongoing need to change prompts and models without breaking things. This is the phase that separates a working prototype from something that stays up at 3am when a provider has an incident.

phase objectives

A model gateway that abstracts providers, handles failover, enforces rate limits. The objective is a single point of control between the application and every model call it makes. Without this, provider-specific logic (auth, retry behavior, rate-limit handling) gets scattered across the codebase, and switching providers or adding failover means touching every call site instead of one component.

Caching layers to cut latency and cost. Two distinct forms of caching are needed because they solve different problems: reusing an exact repeated prefix (cheap, precise) versus reusing an answer to a similar-but-not-identical question (more powerful, riskier). The objective is having both, applied appropriately.

CI/CD for prompts, models, and vector indexes as first-class deployable artifacts. This is a mindset shift worth naming directly: a prompt change is a deployment, with the same rigor as a code deployment — versioned, tested against regressions, and rollback-capable. Same for a vector index update. Treating these as "just config" rather than deployable artifacts is how regressions ship silently.

system components & topologies

Model Gateway. A single ingress point in front of every model call, responsible for: provider routing — directing traffic to the right provider/model based on the routing policy from Phase 2; load balancing across API keys/regions — spreading load to avoid hitting per-key rate limits when a single key would bottleneck things; automatic failover — if Provider A times out or rate-limits, the gateway retries against an equivalent-tier model from Provider B, transparently to the calling application code; request queueing under rate-limit pressure — instead of every request failing immediately when a limit is hit, the gateway can queue and smooth out bursts; centralized logging/cost attribution — every model call passes through one place, making it possible to attribute cost and usage back to features/teams without instrumenting every call site separately. This is the same architectural pattern as an API gateway in a traditional microservices system — the difference is what sits behind it (model providers instead of internal services) and the specific failure modes (rate limits, token costs, model-quality equivalence) it has to handle.

Caching layers. Exact-match prompt caching: providers now offer native prompt caching — a static prefix (a large system prompt, or the retrieved RAG context if it doesn't change within a session) gets marked cacheable, and the provider only charges/processes the delta on subsequent calls that share that prefix. This is a large win specifically for RAG systems, where the same lengthy context block often gets re-sent across multiple turns of a conversation. Semantic caching goes further — caching by embedding similarity of the query, not exact string match. A new query that's semantically close to a previously answered one ("what's your return policy" vs. "how do returns work") can return the cached response without a model call at all, implemented with Redis plus a vector similarity check (the pattern popularized by GPTCache), or a dedicated semantic caching layer. The distinction matters: prompt caching saves cost/latency on the same conversation reusing the same context; semantic caching saves cost/latency across different users asking similar questions — much more powerful, but riskier.

CI/CD for AI artifacts. Prompt versioning: prompts live in version control (or a dedicated prompt-management platform), tagged and deployed like code — meaning a prompt change goes through the same eval-gated promotion process as a code change, and must pass the Phase 5 eval suite before it's allowed into production. This is what prevents "someone tweaked the system prompt in the console and quality silently dropped." Vector index updates: blue/green deployment for the index — build the new index version alongside the old one, validate retrieval quality against the eval set, and only then do an atomic swap to the new version. This avoids the failure mode of serving a half-updated index (some documents re-indexed, some not) mid-update, which produces inconsistent, confusing retrieval results.

tooling & tech stack

  • Gateways: LiteLLM Proxy (the most commonly adopted open-source option, extending the routing library from Phase 2 into a full proxy service), Kong AI Gateway, Portkey, Cloudflare AI Gateway, or AWS Bedrock's built-in cross-region inference/failover for an already-AWS-native stack — often the lowest-friction starting point before reaching for a separate gateway product.
  • Caching: Redis for both exact and semantic caching, native provider prompt-caching APIs (Anthropic and OpenAI both expose this directly), and GPTCache as a purpose-built semantic caching library for more out-of-the-box tooling than building the Redis + similarity-check logic from scratch.
  • CI/CD: GitHub Actions/GitLab CI running promptfoo/Ragas eval suites as a merge gate — the mechanism that turns Phase 5's evaluation harness into an enforced deployment gate rather than a manual check. Terraform for infra-as-code on the vector DB and inference cluster resources.
  • Serving infra: vLLM/TGI running on Kubernetes via KServe or Ray Serve for self-hosted models with GPU autoscaling — directly analogous to running any autoscaled workload on EKS, just with GPU-aware scheduling instead of CPU-based. Managed endpoints (Bedrock, Vertex AI) trade some control for dramatically reduced ops burden — worth defaulting to unless there's a specific reason (data residency, cost at extreme scale, custom fine-tuned model) to self-host.

trade-offs & challenges

Failover correctness: naively failing over to a different model provider mid-conversation can silently change output quality, style, or even safety posture — a response from Provider B might be subtly different in tone, verbosity, or willingness to answer certain questions than what the user was getting from Provider A. Mitigation: only failover between models explicitly validated as equivalent-tier through the Phase 5 eval suite (not just "similarly priced" or "similarly named"), and log/flag every failover event so it's reviewable — if failovers are happening often, that's a signal worth investigating on its own, not just a resilience feature quietly working.
Cache staleness vs. hit rate: the direct risk that comes with semantic caching's power — aggressively caching by similarity means an outdated answer can get served when the underlying data has changed, even though the query is one that's been semantically seen before. Mitigation: bind cache entries to a TTL tied to the Phase 3 data-freshness SLA (if the staleness bound is 15 minutes, the cache shouldn't outlive that), and wire cache invalidation directly to source-document update events rather than relying purely on time-based expiry.
Rate-limit queueing under burst load: a naive retry-with-backoff strategy, applied uniformly across many concurrent requests, can actually make an outage worse — everyone backs off and retries in roughly the same window, creating a retry storm that hits the already-struggling provider with a synchronized burst right as it's recovering. Mitigation: circuit breakers (stop sending requests to a clearly failing provider instead of retrying blindly), jittered backoff (randomize retry timing so requests don't cluster), and load-shedding — deliberately rejecting or queueing lower-priority requests first during a degradation event, so the highest-priority traffic keeps getting served.
GPU cost vs. latency for self-hosted models: a classic capacity-planning tension, just with GPU economics instead of CPU — under-provisioned GPU pools cause request queueing and latency spikes exactly at peak traffic, the worst possible time; over-provisioned pools burn budget on idle GPU capacity, expensive hardware to leave sitting unused. Mitigation: autoscale on queue depth rather than raw CPU/GPU utilization (queue depth reflects actual user-facing pain — a full GPU that's still keeping up with demand doesn't need to scale), combined with scheduled scaling for traffic patterns already known to be predictable (e.g. business-hours usage in an enterprise assistant).

The throughline: every mechanism here — the gateway, the two cache types, the CI/CD gates — exists to make change and failure survivable rather than catastrophic. This phase leans hard on infrastructure patterns already familiar from a traditional AWS/Kubernetes background; the genuinely new part is the specific failure modes (token-cost blowouts, semantic cache staleness, model-equivalence validation) that don't exist in traditional backend systems.

PHASE 7 Monitoring, Observability & Feedback Loops
Read moreShow less

Closing the loop — knowing what the system is doing in production, catching degradation before users complain, feeding real signal back into evaluation.

Phase 6 made the system survive infrastructure failures. Phase 7 answers a different question: how do you know if the system is actually getting worse for reasons that have nothing to do with infrastructure — a subtly degrading model, a corpus that's drifted from what users are actually asking, hallucination creeping up quietly. This is the phase that closes the loop back into everything before it.

phase objectives

Know what the system is doing in production. Not "is it up" (that's Phase 6's job) — but "is each individual request behaving correctly, and can I reconstruct exactly what happened when something goes wrong?" The objective is full traceability, request by request.

Detect degradation before users complain. This is the objective that separates reactive operations from proactive ones. User complaints are a lagging indicator — by the time enough users notice and report something, a meaningful volume of degraded responses has likely already been served. The goal is catching the signal earlier than that.

Feed real-world signal back into evaluation and retraining. This is what makes Phase 7 a loop rather than a dead-end dashboard. Everything observed in production — feedback, flagged interactions, drift signals — should flow back into the Phase 5 eval set and, where relevant, into fine-tuning data. Without this feedback path, observability is just a read-only window; with it, the system actually improves over time based on real usage.

system components & topologies

Full-stack tracing. Every request gets captured as a trace, broken into spans — one span per meaningful step: retrieval, each individual tool call, each LLM call — with token counts, latency, and cost attached to each span individually, not just the request as a whole. Why span-level granularity specifically, rather than one aggregate log line per request: when something goes wrong (slow response, wrong answer, unexpectedly expensive request), it matters which step caused it. A request that took 6 seconds could be 5.5 seconds of retrieval and 0.5 seconds of generation, or the reverse — those point to completely different root causes and completely different people to page. This is the production-time realization of the Phase 1 latency waterfall: the budget was set per-hop at design time, and this is how it gets verified per-hop in reality.

Drift detection, three distinct kinds. Data drift — the distribution of incoming queries shifts away from what the system was designed/evaluated against; e.g. an internal knowledge assistant built for engineering questions starts seeing a growing share of HR questions after a company reorg, a distribution the system wasn't evaluated for. Embedding drift — the semantic distribution of retrieved content shifts over time, a signal that either the corpus itself has changed shape (lots of new documents in a previously underrepresented topic) or user intent has moved in a way that's pulling different parts of the index than before. Semantic/output drift — the model's responses gradually change in character (length, tone, hallucination rate) without any deployment on your side causing it; this is the specific, important case where an upstream provider silently updates the underlying model version behind an API, and the system's behavior shifts even though nothing changed on your end. Catching this requires monitoring outputs over time, not just inputs.

Hallucination tracking. Rather than treating faithfulness scoring (from Phase 5) as a one-time eval-suite check, it runs continuously as a sampled monitor against live production traffic — alerting when the faithfulness score trend drops below a threshold. This turns a pre-launch quality gate into an ongoing health metric.

Feedback capture. Explicit — thumbs up/down, a correction the user submits directly — clear signal, but low volume (most users don't bother clicking feedback buttons). Implicit — the user rephrased their query (a sign the first answer didn't land), abandoned the session, or escalated to a human — much higher volume, but noisier to interpret. Both get piped back into the eval golden-set pipeline (Phase 5) and, where the interaction is a good training example, into fine-tuning data (Phase 2's fine-tuning path).

tooling & tech stack

  • Observability platforms: LangSmith, Arize Phoenix, Arize AX, Langfuse, Datadog LLM Observability, and Honeycomb (when instrumented with OpenTelemetry's GenAI semantic conventions) — these give the trace/span view described above, purpose-built for LLM call chains rather than generic APM.
  • Tracing standard: OpenTelemetry (OTel), specifically its GenAI semantic conventions — the vendor-neutral instrumentation layer, meaning no lock-in to one observability platform's proprietary SDK. The same instrumentation discipline as distributed tracing in a microservices system (OTel spans across service calls), applied here to spans across retrieval → tool calls → generation instead of across services.
  • Drift/anomaly detection: Arize or WhyLabs for embedding and data drift monitoring specifically; for a more DIY approach, statistical tests like Population Stability Index (PSI) or KL divergence run directly against embedding distributions over time windows.
  • Feedback pipelines: product-side event logging (Segment/Amplitude) joined with trace IDs so a feedback event can be traced back to the exact request/response/context that produced it, feeding a labeling queue (Label Studio) where humans review flagged interactions before they're promoted into the eval set.

trade-offs & challenges

Observability cost/volume: full tracing of every single request at high traffic volumes is genuinely expensive to store and query — trace storage costs scale with volume, and a busy production system generates a lot of it. Mitigation: tiered sampling — capture 100% of traces for errors or flagged/low-confidence content, and statistically sample the rest, while retaining the ability to force full-trace capture on demand (e.g. temporarily, when debugging a specific reported issue).
Drift alerts without action paths: detecting drift is close to useless if there's no defined owner and no defined response — an alert that fires and gets acknowledged but leads nowhere is worse than no alert, because it trains people to ignore alerts generally. Mitigation: every drift alert type maps to a documented runbook (re-index the corpus, re-tune router thresholds, escalate to the model provider if it's suspected output drift from their side) with a named owner, the same discipline applied to any production alert in a traditional system.
Feedback loop bias: relying only on explicit feedback overrepresents the extremes — users who are highly engaged (power users who bother to click thumbs-up) or highly frustrated (angry enough to leave negative feedback), while the large middle of "mostly satisfied, didn't bother to say anything" goes unrepresented. Mitigation: weight implicit signals more heavily in aggregate quality tracking, and run periodic blind quality sampling — pulling a random sample of production interactions for human review, independent of whether users flagged them — to get an unbiased read on actual quality.
Attribution across a multi-agent/multi-model system: when quality degrades in a system with multiple agents, multiple model tiers (from Phase 2's routing), and multiple prompt versions in flight, pinpointing which specific component caused the regression requires the span-level granularity described above — flat, aggregate request logging simply doesn't have the resolution to answer "was it the router misclassifying complexity, the retrieval step, or the new prompt version shipped yesterday?" This is the practical payoff of investing in proper tracing early rather than bolting it on after a production incident makes the gap obvious.

That's Phase 7, and it closes the loop: the drift signals, faithfulness scores, and feedback captured here feed directly back into Phase 5's eval set, which gates Phase 6's CI/CD deployments, which in turn get observed again here. The system isn't "done" after launch — this phase is what makes continuous improvement a designed mechanism rather than something that happens by accident when someone notices a problem.

Capstone Walkthrough

Enterprise Knowledge & Action Assistant

This is where everything from Phases 1–7 gets applied to one concrete system, so the decisions can be seen interlocking rather than existing as seven separate frameworks. Below: the scenario, then each phase's application, then the diagram — the reasoning at each step, not just the design restated.

The scenario

A single assistant that does three genuinely different things: answers employee questions from RBAC-scoped internal documents (RAG); answers live data questions via SQL tool-calling ("what's the status of order #4521"); and triggers real workflows ("submit a reimbursement request"). This is a good capstone because it forces every phase's decisions to interact with each other — a design choice in Phase 2 (how to route between these three) constrains Phase 4 (which agent topology handles each), which constrains Phase 5 (what guardrails each path needs), and so on. A toy single-purpose RAG bot wouldn't expose those interactions.

Applying the 7 phases

Phase 1 — classification and NFRs. The first move is applying the deterministic/probabilistic split within this one system, because it's not uniform across the three capabilities. Document Q&A is genuinely probabilistic — open-ended language understanding over unstructured content, needing an LLM. "What's my PTO balance" looks like a natural-language question but is actually a deterministic lookup wearing conversational clothing — the LLM's job is narrow: understand the request and phrase the response, not "reason" about the answer; the actual data fetch is a direct SQL/API call with one correct answer. This distinction is why the system isn't "one RAG pipeline" — it's three different execution paths sharing infrastructure, decided at Phase 1 and made concrete at Phase 2. NFRs get set per path, because they're not uniform either: RAG queries tolerate more latency (users expect "let me look that up" to take a moment) at TTFT < 800ms and p95 < 4s, while SQL lookups are expected to feel instant — p95 < 2s — because the user's mental model is "this is just a database question," even though an LLM is involved in phrasing it.

Phase 2 — routing and model tiering. A router classifies incoming intent into one of three buckets: knowledge_query, data_query, action_trigger. This router is the decision-tree gate from Phase 1, made concrete — the component that actually enforces "don't send deterministic work through the expensive probabilistic path." Model tiering follows the complexity of each path, not a single system-wide model choice: knowledge queries (RAG) get a mid-tier model — enough reasoning capability to synthesize an answer from retrieved chunks, without paying for a top-tier model's cost on every document lookup; data/action queries get a fast, cheap model — because the task is precise structured tool-calling (generate the right SQL, call the right function with the right arguments), not creative synthesis, so accuracy on structure matters far more than reasoning depth; complex cross-domain questions ("compare this quarter's expenses against last quarter and explain the variance," touching both RAG and SQL) escalate to the largest model, because this genuinely needs multi-step planning across data sources. This is the cascade pattern from Phase 2 applied concretely: cheap and fast for narrow, structured tasks, expensive and capable reserved for genuinely complex reasoning.

Phase 3 — retrieval and governance. The document corpus is ingested with ACL metadata tagged per source system — HR documents tagged with HR access scope, Legal with Legal's, Finance with Finance's. Hybrid retrieval (BM25 + vector) applies the RBAC filter at query time, meaning the enforcement point from Phase 3 — pre-filter, not post-filter — is what guarantees a query never even scores documents outside the requesting employee's access scope. An employee in Sales asking a cleverly-phrased question can't surface HR salary data, because those chunks are never candidates for retrieval in the first place, not because a downstream filter caught them.

Phase 4 — orchestration. A LangGraph orchestrator with three nodes maps directly onto the three intent buckets from Phase 2. Retriever node: runs the RAG pipeline. SQL Tool Agent: parameterized, running under a read-only database role, with schema-validated queries — the deterministic-execution principle from Phase 4 applied directly, the LLM decides what to query, but the execution is constrained to a role that can't write or delete, regardless of what the model generates. Workflow Trigger Agent: writes are idempotent (an idempotency key per submitted request, so a retried "submit reimbursement" call doesn't create a duplicate), and — critically — requires an explicit user confirmation step before executing, the human-in-the-loop interrupt pattern from Phase 4: anything with real side effects pauses for confirmation rather than executing autonomously. Memory splits the same way Phase 4 specified: short-term session buffer for conversation coherence, long-term memory for standing user preferences ("always show me EMEA numbers first") that should persist across sessions without needing to be re-stated.

Phase 5 — guardrails. Two guardrails are worth highlighting because they're tailored to this system's specific risks, not generic. Every SQL-generating call passes through a guardrail that allow-lists read-only query patterns against the known schema — a much stronger defense than a generic toxicity/safety classifier, because the actual risk here is a hallucinated or malicious query attempting a write or an unauthorized join, not offensive language. RAG answers run through the faithfulness check before returning — verifying the answer is actually grounded in the retrieved chunks, not embellished. Workflow-trigger actions get logged as high-risk spans regardless of whether the guardrail passed — because a passed guardrail check isn't the same as "this was definitely the right action to take"; high-risk actions deserve audit visibility independent of automated checks clearing them.

Phase 6 — infrastructure. The model gateway sits in front of the router with failover between two providers — applying the equivalence-validated failover principle from Phase 6, not a naive "just try the other one" fallback. Semantic caching is applied specifically to the knowledge-query path, because enterprise FAQ-style questions repeat heavily ("what's our WFH policy") — exactly the pattern semantic caching is good at, and it wouldn't make sense to apply the same caching strategy to the SQL/action paths, where answers are user-specific and shouldn't be cached across users at all. Prompt/router CI gates block any change that regresses the eval suite. The vector index updates incrementally every 15 minutes via CDC — the freshness/cost trade-off from Phase 3, made concrete with an actual number.

Phase 7 — observability. Full OTel tracing with span breakdown per request — router decision, retrieval, tool call, generation — so a slow or wrong response can be attributed to the exact step, exactly as the Phase 7 rationale described. Faithfulness scoring runs on 100% of RAG responses rather than sampled, because at this system's volume it's cheap enough — a direct application of the tiered-sampling trade-off from Phase 7 (sample when volume makes 100% expensive; don't sample when it doesn't). Explicit thumbs-down feedback routes to a human review queue and folds into the golden eval set weekly, closing the loop back into Phase 5.

Reading the architecture diagram

Walking the diagram top to bottom, each layer corresponds to one phase's decisions. Employee → API Gateway (AuthN/AuthZ) → Intent Router: the gateway establishes identity and roles before anything else happens — this is what makes RBAC filtering possible downstream; the system has to know who is asking before it can decide what they're allowed to retrieve. Intent Router → [RAG Retriever | SQL Tool-Calling | Workflow Trigger]: this is Phase 2's routing decision made structural — three genuinely separate execution paths, not one generic "agent" that decides everything ad hoc per request. Each path → its own backing store (Vector DB / SQL read replica / Workflow engine): notice the SQL path hits a read replica, not the primary database — a detail worth internalizing, probabilistic, LLM-driven query generation should never hit a primary transactional database directly, regardless of how well-guardrailed it is; the replica is a blast-radius containment decision, independent of the guardrails themselves. All paths converge → Model Gateway → LLM (routed by complexity) → Output Guardrails → Response: this convergence point is deliberate — regardless of which of the three paths a request took, it passes through the same gateway, caching layer, and guardrail stack before reaching the user, which is what makes Phase 6's and Phase 5's components reusable infrastructure rather than three separately-built guardrail systems; the safety and resilience layer gets built once, and every path benefits. Response → Observability & Feedback Loop: this closes back to Phase 7, and notably it's drawn as a loop, not a dead end — the drift detection, hallucination sampling, and feedback capture here feed back into the eval golden set (Phase 5) and the routing/model decisions (Phase 2), which is what makes this a system that improves over time rather than a static deployment.

Why this design holds up under interview scrutiny: the point worth taking away from the whole capstone is that a staff-level interviewer isn't scoring for whether a vector DB box and an LLM box got drawn. They're checking whether every arrow in that diagram can be explained — what breaks if this connection isn't here — why the SQL path hits a replica and not primary, why RBAC filtering happens inside the vector DB query and not after, why workflow triggers pause for confirmation while RAG answers don't. Each of those is a specific failure mode from one of the seven phases, and the diagram is really just a compressed record of seven phases' worth of "here's what goes wrong, and here's the decision that prevents it."
